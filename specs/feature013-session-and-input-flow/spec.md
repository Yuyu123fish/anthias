状态：实施中

## 问题与依据

调查基线为 `main @ 4a0c48b3c1c902ceb20ad758cc642a95596d02fa`。当前 Session 已采用 JSONL，但记录进入运行时后，writer、SessionAgent 和 Loop 分别维护消息列表，Context 再按持久身份关联它们。`Message` 与 `DurableMessage` 大量重复，调用方还需要理解 Run lease、不同追加入口和写入后的身份查找。

恢复索引的生产调用先完整读取日志，返回的字节位置没有用于局部恢复；每次追加又重新校验全部记录并刷新索引。此前按编码、查询、清理等职责拆文件，仍未消除这些重复状态和调用协议。文件数与代码行数不作为本 Feature 的完成标准。

普通用户输入在运行中被拒绝，成员输入却通过协调层追加后由 Context 单独读取；日志校验还禁止同一 Run 内出现第二条真实用户消息。这使两种输入难以共享清楚的接收和消费流程。

本地 pi `6160683a4a8012f0d1cd30c145df18b4ca6f5176` 提供了 Entry 构造上下文、steer 与 followUp 队列的参考。采用的是完整 Tool batch 后消费 steer、准备结束执行时消费 followUp 的思路；Anthias 继续保留自身的先持久化后推进约束，不照搬 pi 的延迟落盘、分支管理或扩展框架。

基线存储入口为上述基线提交中的 `apps/agent/src/session/writer.ts`，本 Feature 已将其收束到 [Session](../../apps/agent/src/session/index.ts)。其他入口：[SessionAgent](../../apps/agent/src/session-agent.ts)、[Agent Loop](../../apps/agent/src/agent-loop.ts)、[Context 投影](../../apps/agent/src/context/projection.ts)、[协作投递](../../apps/agent/src/multi-agent/index.ts)。调查结论以基线提交为准，文件链接指向当前实现。

## 用户流程

1. 作为开发者，我希望打开已有会话并继续工作，以便保留完整历史并使用正确的模型上下文。
2. 作为开发者，我希望在 Agent 执行时提交优先插入消息，以便在当前安全交接点之后调整后续执行。
3. 作为开发者，我希望将下一项要求排队，以便当前任务正常结束后再处理，且不提前影响当前动作。
4. 作为开发者，我希望看到消息已排队、已插入或被拒绝，以便区分接收成功与任务完成，继续输入或处理工具审批。
5. 作为开发者，我希望停止、关闭或遇到失败时不被后续队列自动重启执行，以便保持对执行的控制。
6. 作为开发者，我希望查看根与成员历史时能辨认消息来源，以便成员建议不会被当作我的授权。
7. 作为开发者，我希望第二个入口可以只读查看正在使用的会话，以便查阅历史而不争用执行权或触发工具。
8. 作为维护者，我希望沿一个消息提交入口找到持久化、历史与上下文的更新，以便修改行为时不必同步多份独立历史。

## 已确认决定

### 职责与事实来源

| 对象 | 职责 |
| --- | --- |
| Session | 创建、打开、顺序读取、追加、更新压缩导航和关闭；持有已提交 Entry 及持久化资源 |
| Agent 内部 state | 持有历史视图、当前 context、活动 partial、待插入消息与执行状态 |
| Context | 根据 Entry、压缩记录和有效来源构造模型输入；管理上下文选择与压缩 |
| Agent Loop | 推进模型与工具执行，决定输入消费时点；不另存一份完整消息历史 |
| TUI | 提交输入、选择插入方式和展示状态；不持有业务队列、写入器或 Provider |

SessionEntry 是持久事实来源。Session 不再维护一份独立可写的 messageHistory；Agent 的历史与 context 是可重建视图，只能由统一提交与投影流程更新。对外 AgentState 保持只读，模型消息、reasoning 和 Provider 类型继续留在 Agent Module 内部。

### Entry 与消息表达

- 首行 Header 保存 Session 身份、Workspace、根与成员归属，以及当前路径最近已提交压缩节点的引用；未发生压缩时该引用为空。Header 不需要 parentEntryId。后续每行对应一个明确的 SessionEntry；JSONL 的行序是物理追加顺序，Entry 的历史父子关系由 parentEntryId 表达。
- 完成消息只使用一种表达，不再维护与 Message 逐字段重复的 DurableMessage。消息的完成、失败、取消及安全诊断继续如实保存，streaming 状态不得作为已完成消息提交。
- Entry 保留稳定 entryId、时间、顺序与必要的 Run、Tool、授权及来源关联。同文的两次输入不能按正文去重。
- 消息、上下文来源、压缩、授权决定、工具开始、Run 终态、会话使用和协作事实仍保留明确语义；不把它们全部改写为用户对话，也不丢弃恢复或审计所需事实。
- 旧消息格式只在兼容入口归一化。新写入格式显式提高 Schema 版本，版本号和字段迁移映射在 Plan 中列明。
- 活动 partial 仅用于流式呈现；终结时保存最终消息。当前 Run 的临时 reasoning 继续服务模型协议，不因统一 Entry 而扩大其持久化范围；新 Run、压缩和重开仍按既有协议处理。

### Entry 树与 fork 预留

Entry 通过 entryId 与 parentEntryId 构成历史树，parentEntryId 表示历史父节点。本 Feature 只维护其中一条路径：第一条 Entry 的父引用为空，普通追加连接当前路径末端；读取和追加继续校验父引用完整性。当前单路径运行不把树结构改成依赖文件行号的线性记录，也不增加分支创建或切换能力。

后续 fork 的候选方向包括从指定历史位置继续的对话分支，以及与对话关联的 Git worktree 分支。本 Feature 只保留父引用，不建设分支头、分支选择、fork Interface、worktree 创建或两种分支的绑定协议，也不恢复执行分叉作为核心产品前提。

### 压缩入口与前后导航

Header 的压缩引用是构造 context 的起点：“下一个压缩节点”表示从 Header 跳向当前路径最近一次已完整提交的 CompactionEntry，不是按创建顺序指向最早一次压缩。每次新压缩成功发布后更新该入口，普通消息追加不刷新它。

每个 CompactionEntry 额外保存前一个和后一个压缩节点的引用，形成当前路径上的双向压缩链。首个节点的前引用为空，最新节点的后引用为空；相邻引用必须指向同一 Session、同一路径中正确类型的节点，互相对应且无环。这里的前引用指前一次压缩，不等同于 parentEntryId 所表示的历史父节点。

压缩入口与前后引用使用稳定的 Entry 身份关联。已加载 Session 可直接解析这些引用，避免每次构造 context 都遍历整段历史寻找最新压缩；仅保存 Entry ID 并不等于能够直接定位 JSONL 的文件字节。Plan 必须明确查找方式和实际读取范围，继续满足打开时的完整校验，不把内存查找收益宣称为免扫描磁盘恢复，也不恢复逐条刷新的独立 session.index.json。

Context 先检查入口节点在当前来源版本和撤销状态下是否仍可采用，再读取摘要、保留历史的边界或引用、有效来源及其后续消息。入口失效时检查更早候选；没有可用压缩时按原始 Entry 与当前有效来源重建，不能复用失效摘要。保留的原文可能早于压缩节点在文件中的位置，不能只截取压缩行之后的记录；通常只采用当前有效摘要，不将历次摘要简单叠加。前后引用用于导航与一致性检查，需要回退时才沿可信的前引用寻找更早有效节点。

持久化 Header 入口和旧压缩节点的后引用会更新已有记录，因此整个文件不再宣称严格只追加。普通消息和执行事实继续追加；压缩导航采用受控更新，已有消息正文、历史父关系和工具执行事实保持不变。新节点内容完整持久化后，才能将入口及前后关系发布为一致的新状态，再切换运行 context。不能把多个独立字段写入视为一次原子提交；具体候选文件替换或等价可恢复发布方式由 Plan 说明并验证，不直接变长覆盖 JSONL 旧行。

压缩或发布中断后，要么保留此前完整状态，要么恢复完整的新状态，不能使用尚未完整提交的新入口，也不能丢失此前已提交的消息。导航引用缺失、失配或陈旧时，可以依据仍完整可读的记录校验并重建；只有前引用本身可信时才沿链回退。节点损坏导致前引用也无法读取时，双向链不提供独立恢复保证，仍须按日志恢复规则处理或明确失败。只读查询不执行这些修复。

当前单个 next 只表达一条压缩路径。未来同一历史节点若分出多个后继，必须另行定义压缩导航的分支归属；本次父引用预留不代表单条压缩链已支持多分支，也不提前增加分支导航结构。

### 统一消息提交与两个视图

完成消息经过同一个内部提交入口：形成 Entry → 追加 JSONL 并确认持久化 → 更新历史与 context → 发布完成事件。追加返回已提交 Entry，调用方不再搜索最后一条记录来补回身份。Tool 只返回 ToolResult，不分别写历史和 context。

- history 提取已提交的完整对话及其来源，供展示和回看；审计和恢复事实继续保存在完整 Entry 中。压缩不删改已有对话内容。
- context 是下一次模型请求的消息、摘要和有效来源。普通提交可以增量更新；打开、压缩或来源变化时，按统一规则重建，不由多个调用方各自拼接。
- 有效压缩候选先持久化，再切换 context。摘要失败或取消保留原历史与可用投影；完整 ToolCall/ToolResult 组、用户原文保留、来源版本与撤销规则继续成立。
- 同一组已提交 Entry 在正常更新和重新打开后应得到语义一致的历史与 context；仅限当前 Run 的临时协议数据除外。成员输入经过统一输入消费，来源事实经过统一 Entry 提交和投影更新，不由其他调用方直接拼入模型请求。

### Session 写入所有权

可执行 Session 从创建或打开成功起持有独占写锁，直到关闭并释放资源。根与每个成员分别持有自己的 Session；同一个 Session 的消息、上下文与协作事实追加，以及压缩导航更新，共用一个写入器和一条串行写入链，不再逐 Run 获取和释放 SessionRunLease。

另一个进程可以只读查看已提交历史，但不能同时打开同一 Session 执行。只读查询不持有长期写锁、不迁移或修复日志、不要求原 Workspace 仍然存在，也不创建 Agent 或调用模型。执行入口仍核验 Workspace、Session 身份和根归属。

关闭先停止接收新输入，取消并等待已拥有的执行与工具收尾，再等待已接受写入完成，最后释放锁。Run 正常结束不释放 Session 写锁。初始化失败要释放已取得资源；活跃或无法证明已经退出的锁持有者不能被抢占。

每个 Run 只提交一次终态，终态完成事件在该事实持久化后交付。followUp 开始下一 Run 不能越过上一 Run 的封口与资源收尾。

写入失败后停止继续执行和提交完成事件，保留已成功提交的事实，重新打开后按恢复规则处理。入队不等于刷盘，释放锁不能越过尚未完成的已接受写入。

### 减少重复机制

- 删除独立恢复索引生成、逐条刷新与读取依赖；新 Session 不再要求 session.index.json。Header 压缩入口及压缩前后引用只随压缩发布更新，不替代全部历史事实，也不随普通消息追加刷新。旧索引不作为恢复权威，其存在不阻止旧历史读取，也不触发全库删除或迁移。
- 打开日志进行完整校验；正常追加只检查新 Entry 与当前必要关联状态，不重新校验和读取整段日志。外部改写或身份异常仍须被识别，不能静默采用旧上下文继续执行。
- 删除正常执行中的双向消息复制与身份回查，以及 Session、SessionAgent、Loop 各自维护完整历史的流程。
- 正常阅读集中到 Session 生命周期与读写、Entry 定义与校验、Context 构造。清理组装并入清理私有实现，兼容迁移集中，Tool 产物由独立资源模块持有；不为缩短文件机械新增转发层。
- 具体文件组织在 Plan 中落实。独立清理进程入口、资源持有与恢复职责可以保留；仅合并或移动文件不能作为上述改造的证明。

## 输入、执行与失败合同

### 接收与消费

| 场景 | 行为 |
| --- | --- |
| 空闲时提交 | 开始新的 Run，初始输入持久化后才推进模型或工具 |
| 运行中 steer | 排队；当前 Assistant 与其完整 Tool batch 收尾后，插入当前 Run，供下一次模型请求使用 |
| 运行中 followUp | 排队；当前 Run 正常结束后，取出下一条并开始新的 Run |
| 当前模型回复没有 ToolCall | 仍检查 steer；没有可消费 steer 才结束当前 Run，并检查 followUp |
| 没有待插入消息 | 按既有执行、失败或完成路径收尾 |

两个 FIFO 队列由 Agent 持有，共用输入接收与消费流程；steer 优先，每次取一条，同队列保持接收顺序。steer 插入后允许同一 Run 出现后续真实用户消息，日志不得继续套用“仅一条起始 UserMessage”的限制，但仍禁止未决 ToolCall 被后续消息越过。

安全点是完整 Assistant 响应及其整批 ToolResult 都已提交之后，不是单个并行 Tool 完成之后。steer 不取消正在进行的模型请求或工具，也不跳过当前批次尚未执行的调用；较长批次会推迟生效。等待审批时，排队不会替代批准、拒绝或停止操作。

输入接收与 Run 结束之间的交接必须有确定顺序。消息不能因恰好遇到最终回答或 run_end 而丢失、被消费两次，或追加到已经封口的 Run；若 Run 已经终结，新输入归后续 Run。

### 受理、呈现与持久化

- 提交入口区分受理、排队和拒绝；受理回执不冒充执行完成。队列项目有可关联的输入身份、来源与模式，消费时关联实际 Run 和已提交 Entry；执行结果由 Agent 状态与事件交付。
- TUI 不能等待整个 Run 完成才允许下一次正文提交。全屏和纯文本入口都应能明确选择优先插入或等待插入，并显示待处理及已插入状态；具体按键和命令形式由 Plan 给出，不另建 TUI 业务队列。
- 普通队列只在内存中保存，排队回执明确表示尚未进入持久历史。只有消费并成功提交 Entry 后，消息才进入正式 history、context 和用户授权来源。
- 排队中的 followUp 不影响当前任务；待消费 steer 同样不提前进入请求或授权判断。已有独立权限撤销、审批和 abort 行为不等待输入队列。
- 普通队列不跨重启恢复，也不转移到另一个 Session。关闭或切换时，未消费输入的处理结果必须对用户可见，不能报告为已经保存的对话；已有持久历史不受影响。

### 停止、失败与继续

用户停止、终态失败或关闭后，禁止自动消费队列重新启动 Agent。停止或失败后，当前进程中的未消费普通输入保留为待处理，开发者明确继续后才恢复消费；关闭或成功切换 Session 后释放其内存队列。关闭中拒绝新输入，不允许迟到的模型增量或工具结果恢复执行。

沿用现有有界模型重试和压缩恢复；这些内部恢复不算当前 Run 正常完成，也不触发 followUp。存储或 Session 身份失效时必须先恢复会话，不能仅凭继续命令沿用失效写入器。已提交消息不会因取消被重复写入，副作用不得因恢复或队列重试而重新执行。

### 用户与成员输入

用户和成员输入共用最终接收、排队和消费入口，但保留可校验来源。成员输入、摘要、ToolResult、Skill 与 MCP 内容不能成为真实用户授权；AutoAllow 继续核验已消费、已持久化的真实用户原文及当前有效权限。

已有协作投递仍保存 coordination、agent_input、稳定 messageId 和根与来源 Session 身份，不降级为普通内存队列。保持根入队事实先持久化、目标输入落盘后根才确认送达的顺序。运行中的既有成员消息在相同安全点消费；成员空闲或会话重开时仍不因待投递记录自动调用模型，须显式继续既有协作。统一消费不能把 delivery 的恢复记录与运行内存重复排队，也不新增自动唤醒成员或任务调度能力。

### 必须保留的恢复与资源行为

- ToolCall 与 ToolResult 完整配对并按既有源序保存。恢复时区分未开始和已经开始但结果未知的调用，不将未知结果伪装为成功，也不重放副作用。
- 只修复可证明为 EOF 截断的未完成尾段；中间损坏、非法完整记录或身份冲突明确失败，不静默丢弃历史。
- 根与成员继续各自拥有历史、产物额度和取消资源。共享权限与 MCP 生命周期、请求工具快照、执行前复核、既有工具并发上限和任务时限保持。
- 新根与成员保留既有嵌套存储布局。Schema 1/2/3、旧平铺与混合布局继续可读；只读操作不改写，写入升级只针对明确打开且已取得写锁的 Session，保留可恢复旧事实，不做全库批量迁移。
- 清理继续保护整个根成员组、活动持有者、未知状态和未交付成果。Session 空闲但仍持有执行写锁时也受保护；移动前持久化清理意图，中断后恢复或保守保留，不删除 Git worktree、项目文件或分支。
- 只读历史若遇到正在追加的末尾，最多返回可验证的完整已提交前缀或明确可重试结果，不修复活动文件或把暂时未完成尾段当作可删除数据。

## 不在范围内

- 对话分支创建、分支头管理、历史分支选择、fork Interface、Git worktree fork 或分支绑定。
- 立即取消请求或工具来抢占输入、跳过当前 Tool batch、重放工具副作用。
- 普通输入队列跨进程或跨重启持久化、可靠消息中间件、成员自动唤醒或新的协作调度器。
- 数据库、OS 沙箱、Provider 专用实现、通用 Registry、额外 package 或传输协议。
- 改写所有旧历史、批量迁移数据目录、改变工具产物预算或扩大成员权限。
- 无关工具、记忆、MCP 或 Git 功能重构；真实模型和外部服务验证。
