## 顺序与失败边界

命令 timeoutMs 保留执行时间含义，取锁另以同一数值为等待上限，结果区分等待、执行和 processStarted。取消等待不会启动进程；取消执行需等待原命令的清理宽限。

恢复的资源检查最多等待两秒，同一阻塞的并发恢复复用当前检查。检查失败或保存/删除记录失败保留保护。运行时不使用可能复用的裸 PID 再次发起终止；重启只有已保存的阻塞事实，没有原句柄时需外部检查和用户确认。`workspace-blocks/*.resolved` 保留解除依据；未发生阻塞的普通命令不逐条建立新日志。

Esc 只等待被中断 Run 自己产生的阻塞，不等待所有成员，也不被旧 Run 的阻塞拦住纯模型对话。输入在历史提交成功后才离队，正在持久化的输入不能再次领取。已经成功的工具结果保留，未完成调用按实际终态封口。旧 Run 终态保存失败仍使群组停止，不因输入中断标记而被忽略。

Session 继续使用 Schema 4，新请求配置字段可选；旧记录缺少时保持未知。恢复不扩大成员能力、三种权限模式、十个执行并发或 worktree 边界。

### 通用修复与失败边界

- 分别记录进程 exit、stdout/stderr 自然结束及 close。主进程已退出但输出仍未结束时，短宽限后返回 `output_pending`，保持写入保护，不再按已退出进程的 PID 发起终止。
- 收尾只移除本模块的数据监听，保留 Node 内部生成 close 所需的监听。资源自然结束后能观察到新事实，历史终止失败不再永久否决恢复。
- 根的 `agent_recover_workspace` 和用户的 `/agent recover` 有界重查原执行器仍持有的命令进程和输出流，必要时重试通用终止。检查最多两秒，支持取消，不经过被阻塞的写入队列，不接收任意清理 Shell 或孤立 PID，不重放工具。
- 外部资源仍持有句柄、持有关系丢失或清理持续失败时保持阻塞；由外部工具或用户清理后重查，必要时使用直接用户确认。普通对话“已清理”不等于 `/agent recover <blockId> confirm-cleanup`。

这次修复解决 Anthias 在资源实际结束后仍无法恢复的问题。它没有修复 agent-browser 自身的 Windows 句柄行为；原 PowerShell 管道组合仍可能挂起，不能承诺未知外部资源可以自动恢复。
