# Feature 014 实施报告

状态：已实现

## 开发者速览

> **一句话**：根 Agent 统一管理持续成员，成员通过持久邮箱与共享笔记协作，默认直接使用根工作区。<br>
> **核心做法**：统一生命周期与暂停来源；文件内容版本加可取消写入协调；三种权限与 TUI 入口保持一致。<br>
> **边界**：含根十个执行位置，仅本进程受管操作；按需创建工作树，兼容旧历史。<br>
> **风险 / 未验证**：首次全量中 Git 与本地 HTTP 各有一次失败，定向未复现；未做真实 Provider 或人工终端体验验收。<br>
> **当前 / 请审阅**：Spec 先行，完整门禁已通过，待开发者验收。

## 实施范围与结果

开发者于 2026-09-11 授权先保存 Spec，随后连续实施整个 Feature、更新文档并可做中间提交。本次先保存 [Spec](spec.md)、[Plan](plan.md) 和 [Tasks](tasks.md)，再从 main 的 2159f6c1749a902d8832b9761d8ad22b5c243ebe 创建 codex/feature014-unified-multi-agent 分支。原有 agent-loop.ts 工具调用注释保持原样，不纳入 Feature 提交。

统一群组属于根 Session，首次创建成员即可使用。成员具有各自的 Session、上下文和 Run，正常一轮结束进入 idle；超出九个成员执行位置的任务排队，为根保留第十个位置。普通成员只能通信、更新自己的任务与访问公开协作状态，根保留创建、正式分派、暂停、关闭、重开、工作区绑定和 Git 成果交付权。

邮箱在根日志保存稳定消息 ID、发送者、接收者、时间、任务关联和状态。成员输入持久化后才确认消费，忙碌时在完整工具批次后的安全点插入，空闲时由统一调度唤醒。每个收件者最多三十二条待处理消息，单条十六 KiB；重复 ID 不重复执行，冲突 ID 和容量超限明确拒绝。

根 Session 目录只维护一份 shared-notes.md，最大二百五十六 KiB。所有成员可以读取与追加，根携带内容版本重整全文；写入串行、原子替换并记录作者和修订。普通代码工具不能直接访问受保护的 Session 目录，笔记不充当权限来源，也不自动广播。

权限入口仅保留 agent、auto_allow、full_access。请求批准模式自动允许只读与受管组内协作，其他副作用逐次批准；AutoAllow 独立审核普通必要副作用，极高风险转人工，故障不视为批准；Full Access 跳过批准，但不取消成员只读、所有权、版本前提与资源约束。直接用户协作命令先持久化 user_request，审核可以核验真实任务来源；成员邮箱和笔记仍不能产生用户授权。

成员默认可写且共享根工作区，只读约束与工作树选择独立。需要隔离时先显式创建受管工作树，再绑定停止中的成员。重开核对根日志中的当前绑定与所属关系，不改写原 Session Header，不复制未提交文件、依赖、凭据或后台环境。旧 plan、subagent、teammate 记录继续可读，TUI 不再显示两类成员。

## 关键调用链与并发边界

- Agent.collaboration 与模型 agent_* 工具进入 multi-agent/index.ts；前者由运行时绑定用户来源，后者绑定实际调用 Session。根控制和组内通信在此校验身份，不让消息正文决定权限。
- members.ts 持有成员 Session、执行队列、取消和工作区绑定；tasks.ts 持有正式任务；mailbox.ts 串行持久化投递；shared-notes.ts 串行维护受管笔记。原 agent-team.ts 已移除，不另建第二套模型循环。
- SessionAgent 继续独占 Run 与输入安全点。成员唤醒通过稳定输入 ID 去重并使用同一执行位置；Run 完成后才回收位置，执行中的停止等待清理。根正常完成关闭新唤醒，已启动成员可在原期限内收尾；根失败或取消收束成员。
- read_file 返回完整原始字节的 sha256 内容版本，分页也使用同次完整读取的版本。edit_file 与 write_file 使用 expectedVersion，新建使用 missing。批准之后取得文件写入权，再校验版本、身份、当前授权与取消，并在锁内原子替换。相同字节对应相同版本，不能把摘要解释为递增历史序号。
- workspace-access.ts 在实际路径与文件身份上协调写入；同一文件串行，不同文件可以并行。命令对所属工作区独占，Git 对相关工作区使用同一协调器。等待可取消，批准与模型思考期间不持写锁；命令清理不能确认时保留租约，后续写入不假装安全。

用户暂停来源优先于根。停止或关闭先禁调度，再取消启动、批准、资源等待与执行；控制修订使更早的异步继续不能在后来的停止之后生效。应用退出释放资源但保留 idle/paused 来源，运行中成员恢复为 interrupted；显式关闭保存 closed 并拒收新消息，根需明确重开。重启只恢复事实，用户继续群组后才调度；消息不会重置三十分钟共享时限。

## 独立审查与修复

独立审查对照 Spec 检查了协调层，以及文件写入、权限、Git 与 TUI 接线。四项有效问题均已修复，并补相应定向回归：

1. 用户停止群组后，根曾可通过新建成员绕过暂停。现在同时停止根，持久保存用户暂停来源，并在根控制入口拒绝绕过。
2. 根 Run 失败后成员曾能继续执行。现在在 Run 所有权清理结束后收束成员，正常完成则按 Spec 仅关闭新唤醒。
3. 分派或继续在任务保存处等待时，后来的停止可能被迟到恢复覆盖。现在按成员与群组控制修订重查，停止优先。
4. 排队的新任务尚未开始就停止时，再继续可能取回旧任务。现在入队即保存正式任务与 ID，实际开始才转 running。

Feature 013 的 R01 也已修复：先清除 resumeAfterTermination，再判断 signal 是否已经取消。验证覆盖模型等待与终态记录提交期间的停止、继续、再次停止。R02–R06 的理解成本问题未在本 Feature 中冒充解决。
