# Feature 008：记忆系统与提示词编排调研

状态：调研完成；后续决定见 [Spec](spec.md)，已完成实现与本地验证，证据见 [Report](report.md)。

## 开发者速览

> **一句话**：主动记忆需要完整的维护与遗忘闭环，缓存优化首先要减少历史前方的内容变化。<br>
> **核心做法**：对照主流 Agent 与 Provider 官方资料，追踪 Anthias 实际请求装配及持久化路径。<br>
> **边界**：纳入项目规则、记忆、请求编排及固定请求次数截止移除；保留现有压缩主线。<br>
> **风险 / 未验证**：本文保留实施前研究证据；真实缓存收益尚未测量。<br>
> **当前 / 请审阅**：已完成方案收束和实施；下文基线描述固定在调研时点。

基线核验日期：2026-09-06。仓库：`main`，HEAD `a56c921adf91199ca57a68a0b0c3d99389d6bfa2`。2026-09-07 补充后续讨论并形成 [Spec](spec.md)。研究阶段未修改业务代码；后续实施结果单独记录于 Report。

## 研究问题与结论

本轮回答两个问题：Anthias 怎样主动积累可跨 Session 使用的偏好、习惯与经验；已有请求怎样在正确提供上下文的同时增加缓存复用机会。

两条主线共同决定下一次请求，但职责不同：记忆决定保存、选择和复核什么；编排决定已选择内容的位置、版本和注入时机；Provider 缓存复用相同输入前缀的计算。记忆的事实有效期与 Provider 缓存存活时间分别管理。

当前最明确的发现是：

1. Anthias 已有历史、摘要和外部来源持久化，尚未形成跨 Session 的主动记忆闭环。
2. 比起调整几行基础提示词，优先处理 Skill / MCP 正文在会话历史之前被重新拼装的问题，收益机会更直接。
3. 长期偏好、项目事实、临时状态需要不同的失效条件；一律按若干天删除会同时误删偏好、保留错误事实。
4. 可以先用少量本地文件、紧凑索引和有来源条目形成闭环。向量检索、后台整理 Agent、跨设备同步是否必要，需由记忆规模与召回效果证明。

主流 Agent 的主动写入、作用域、检索和时效机制见独立的[记忆专项研究](research-agent-memory.md)。下文记录 Anthias 基线、缓存一手证据和项目推断。

### 当前请求实际怎样组成

```text
SessionAgent.prompt
  → 接纳并持久化真实用户输入或有来源的内部输入
  → createCodingSystemPrompt(workspaceRoot, shell, permissionMode)
  → Agent Loop：消息历史 + 内置工具 + Git / 协作工具
  → Context：投递成员输入、external.project、历史投影、预算检查
  → OpenAI-compatible Adapter：system + messages + tools
```

普通请求中，系统字符串的顺序是：

```text
Anthias 身份
工作区路径 / 平台 / Shell / 权限模式
工具说明 / 证据与执行规则
Skill 目录元数据
外部内容来源边界说明
已激活的 Skill、Skill 引用、MCP Resource / Prompt 正文
```

上述字符串整体位于 `messages` 之前。`messages` 是原历史，或“压缩摘要 + 保留原文 + 新消息”；Tool definitions 是单独的请求字段。模型服务最终如何排列工具和消息，取决于协议与 Provider，移动 JavaScript 对象属性不能控制它。

定位依据：`session-agent.ts:778–817`、`agent-loop.ts:287–305`、`context/index.ts:150–175`、`external-capabilities.ts:161–240`、`model/openai-compatible-model.ts:27–45`。

### 缓存相关问题及其影响范围

| 现状与位置 | 原因及影响 | 研究建议 |
| --- | --- | --- |
| 工作区等信息位于基础规则前方，`coding-system-prompt.ts:18–28` | 同一 Session 通常不变；不同项目、worktree 或权限模式会较早产生差异 | 将真正通用的规则放前；按同会话、跨会话、根/成员分别评估复用 |
| `external.project` 每次把活动正文拼入 system，`:169–173,239` | 新增或替换来源后，变化点后面的整段历史不再匹配旧前缀；`load_skill` 在同一 Run 内就能触发 | 按需正文以有来源的增量进入会话投影，并保留明确的加载/移除/刷新语义 |
| `activeSources` 按 Map 插入顺序呈现 | 相同集合由不同顺序激活，可能得到不同文本；稳定会话本身不会每次随机重排 | 无序目录与 schema 做确定性排序；有语义顺序的指令和消息保留原序 |
| MCP 定义按配置连接及服务端列表顺序呈现，`mcp/index.ts:324–331` | 重连或服务端返回顺序改变，可能改变定义序列；增加/删除工具也会改变请求 | 稳定名称、描述、schema 和排序；工具可见性与权限变化仍必须如实生效 |
| Reasoning 仅在当前 Run 的 continuation 中保留 | 新 Run 或恢复时其移除可能改变较早的 Assistant 消息 | 将其视为已知失效原因，保留现有短生命周期合同 |
| 压缩替换早期模型历史 | 前缀从摘要处发生真实变化，压缩后需要重新积累会话缓存 | 接受必要重建；衡量整项任务成本、恢复质量与重复工作 |
| 摘要和审批使用各自的 system、空工具表和有界来源 | 它们通常无法复用普通请求的完整前缀 | 分用途观测；不能为共享缓存扩大审批可见来源或破坏摘要预算 |

`context/request.ts:13–49` 的 `contextVersion` 与 `UsageAnchor` 用于本地 token 估算校准，并未发送给 Provider。锚点失效不能直接解释为服务端缓存全部失效；锚点有效也不能证明命中。当前代码已有合理的固定工具顺序和历史追加行为，不应把所有请求描述为不可缓存。

## 提示词编排的一手证据

### Claude Code：稳定前部，按需内容追加

官方说明按核心配置、项目上下文、会话排列；项目上下文包括规则与 auto memory，在会话开始或 clear/compact 时装载。Skill 和模式指令可追加为消息。压缩会重建会话层；其摘要请求尝试沿用原上下文。此证据描述 Claude Code 的产品行为，不能直接转成 Anthias 当前具备的能力。[Claude Code 缓存说明](https://code.claude.com/docs/en/prompt-caching)

**项目推断：** 记忆存储更新与当前请求前缀更新可以分开。保持会话初始的有界记忆视图，后续新记忆、纠错和按需正文追加为带来源的内容，在重建投影时重新选择有效条目。不能为了保留缓存而延迟用户要求立即生效的纠正或遗忘。

### Provider 规则需要按实际模型与接口区分

| Provider | 本次核验的事实 | 对当前 Anthias 的意义 |
| --- | --- | --- |
| DeepSeek | 默认启用；需要完整匹配已落盘的前缀单元。文档示例中 `A+B` 后接 `A+C`，公共 `A` 可能在第二次请求后才落盘，第三次才复用；命中尽力而为 | 稳定前缀有价值，但两次请求不足以证明公共前缀稳定命中。[官方说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/) |
| OpenAI | 匹配服务端渲染后的完整前缀；工具定义及其顺序也影响匹配。支持的缓存模式、阈值和保留设置依模型变化，`prompt_cache_key` 影响路由而不保证命中 | 不把某代模型的阈值或 API 字段固化成通用策略，也不能将 Responses 示例当 Chat Completions 已接入能力。[官方说明](https://developers.openai.com/api/docs/guides/prompt-caching) |
| Anthropic | 缓存按 tools → system → messages 依次受影响；支持自动断点和显式 `cache_control`，可用 TTL 与平台有关 | 提示词位置与 Provider 标记是两层问题；当前兼容 Adapter 未暴露这套控制。[官方说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) |
| Gemini | 当前文档强调相同前缀的隐式缓存；Interactions 与 generateContent 对显式缓存的支持不同 | “模型支持缓存”不能推出任意兼容接口支持相同控制。[官方说明](https://ai.google.dev/gemini-api/docs/caching) |

这些网页于 2026-09-06 核验，后续可能更新。本轮未采用二手文章中的统一 TTL、固定分块尺寸或价格承诺，也未请求真实 Provider。Anthias 当前为 `ai@7.0.85` + `@ai-sdk/openai-compatible@3.0.41` 的 Chat Completions Adapter；本轮未确认它能转发以上所有专属参数。

### 建议的编排方向，待 Spec 确认

1. **稳定基础规则与确定的工具定义。** 不混入每轮时间、随机 ID、实时状态；目录、schema 在不改变语义时确定性序列化。
2. **会话初始上下文。** 稳定用户记忆摘要、工作区和环境、项目规则、能力目录与已选择的经验建立有界版本。具体次序见后续讨论输入；完整记忆库按需读取。
3. **按发生顺序增长的会话。** 用户消息、模型消息、Tool 结果、成员投递、记忆读取与上下文更新保持来源及追加顺序。无需重发未变化的记忆全文。
4. **明确刷新与重建点。** 普通规则或记忆变化通过有来源的增量生效；压缩、恢复及用户遗忘需要重新校验有效内容。需要移除的内容不再发送，新的权限限制立即在执行层生效。

这只是内容生命周期的建议，尚未确定具体 role、Schema 或新接口。当前 `ModelInputMessage` 只有 user / assistant / tool，外部来源也只支持四种 kind；增量注入必须与恢复、预算、ToolCall 配对和 AutoAllow 的真实授权识别一起设计，不能把记忆伪造成新用户指令。

## 主动记忆应该形成的用户闭环

以下是结合当前代码提出的候选范围，尚未确认实现：

> 用户纠正做事方式或任务产生可复用经验 → Agent 判断是否值得记住并保存来源 → 后续相关任务自动选用 → 必要时复核 → 用户可以查看、纠正、遗忘或关闭。

### 内容与时效

| 内容 | 例子 | 建议的生效与失效方式 |
| --- | --- | --- |
| 用户明确偏好 | 偏好中文解释、希望先看结果再看细节 | 长期保留，受适用范围限制；用户新表述覆盖旧偏好 |
| 观察到的习惯 | 多次要求某种验证或汇报方式 | 保存观察来源与不确定性；单次表现只作候选，避免把模型推断当用户明示 |
| 项目经验与事实 | 构建入口、容易误用的命令、某个环境限制 | 绑定项目和适用条件；使用前按漂移风险核对代码/配置，变化时替代或失效 |
| 临时约束 | 本周暂不升级依赖、某任务尚未完成 | 明确期限或任务结束条件；到期停止默认注入 |

至少需要分辨来源时间、最后核验时间和最后访问时间。读过一条记忆不代表验证过它；否则错误条目会因频繁召回不断续期。期限到达、条件变化、用户纠正和来源不可用也是不同事件：过期停止默认采用，冲突等待核验或由明确新事实替代，来源已删除则如实标记证据缺口。

自动写入的触发点也需要选择：在执行主循环中提供有界的维护行为，能够及时捕捉明确纠正；Run 结束后的整理便于聚合与去重，但需要额外调用预算和明确取消/关闭归属。建议先形成一种清楚的主动维护路径，额外整理只处理有实际收益的候选。

### 与现有仓库边界的衔接

- **用户与项目作用域。** 用户偏好可跨项目使用；项目事实默认只在该项目生效。Feature 007 的成员可能使用独立 worktree，直接以绝对工作目录作为项目记忆身份会把同仓库切成多个记忆空间；身份与分支适用条件要分别确定。
- **根 Agent 与成员。** 根和成员复用 SessionAgent，但各自有 Session。建议成员读取有界相关视图、提交带来源的候选，由明确的持有者合并；同时考虑两个根会话/进程写入同一记忆时的冲突，不能只锁某一个 Run。
- **持久化与历史清理。** `session/cleanup.ts:32` 仍以 14 天作为过期活动判断的一部分，并按协作关系保护资源。长期记忆不能随单条来源 Session 被清理；保留必要且不含敏感值的证据说明，原始来源删除后不声称仍可回读。
- **保存与召回预算。** 候选提取、去重、相关性选择和注入都有成本。限制条目数量、大小、每次读取和模型维护调用；从紧凑索引与按需读取起步，再用漏召回证据决定是否增加检索设施。
- **授权边界。** 偏好、摘要、外部正文和成员转述都不能变成真实用户授权。`agent.ts:177` 将成员审核连到根 Session 原始记录，`permission/auto-review.ts` 继续限定授权来源；记忆不得改变这个入口或存储敏感凭据。
- **纠正与遗忘。** 除编辑/删除条目，还需定义当前活动上下文、恢复后的旧快照、派生摘要如何停止采用，以及后续整理怎样避免从同一旧来源重新生成已遗忘内容。停止使用与彻底擦除原始历史是不同用户操作，需在 Spec 写清。
- **规则文件。** 当前 Anthias 没有 `AGENTS.md` 自动装载器，开发者已明确将该能力纳入 Feature 008。项目规则与 Agent 学到的记忆保留各自来源，按项目规则 > 有效经验记忆 > 用户记忆处理适用内容间的冲突；具体加载与刷新范围见后续讨论输入。

## 如何判断确实有改善

本轮已执行已有测试：

```powershell
pnpm exec vitest run apps/agent/test/context-integration.test.ts apps/agent/test/openai-compatible-model.test.ts apps/agent/test/agent-capability-boundaries.test.ts
```

结果：3 个文件、24 项测试通过。环境：Windows PowerShell，Node `v24.13.1`、pnpm `10.33.0`、Vitest `4.1.11`。模型流与 HTTP 服务均为本地确定性测试，覆盖上下文校准/压缩、Provider 用量字段及来源失败边界；没有运行整库回归或真实模型，不新增测试代码，不保留后台进程。

后续验收建议分两层：

| 目标 | 可用本地确定性验证的行为 | 仍需要实际使用或另行授权验证的部分 |
| --- | --- | --- |
| 记住且用对 | 项目规则自动加载与三层冲突处理、偏好跨 Session 召回、项目隔离、期限过滤、纠错替代、遗忘不复活、并发更新不覆盖 | 自动采集是否准确、习惯推断是否合理、是否减少用户重复解释 |
| 编排稳定 | 同输入产生相同请求；内容新增只追加；工具顺序稳定；来源/权限与压缩后恢复正确 | Provider 实际缓存命中和时延 |
| 缓存收益 | 对最终 Adapter 请求记录安全的长度/指纹，定位最早变化位置；标记权限、工具、正文和压缩等原因 | 同模型与环境下，对冷启动、续聊、Skill 加载、记忆更新、压缩后续聊进行有限对照 |
| 总体收益 | 保持未知用量为未知，复用现有按用途累计 | token 加权命中率、缓存写入量、首 token 时延、整项任务耗时、额外记忆调用与重复工作 |

token 命中率采用可知样本的 `ΣcachedInputTokens / ΣinputTokens`，同时报告未知字段/请求的覆盖率；若现有累计已经因缺失字段变为未知，不能把它转换成零。缓存命中 token 仍属于模型输入，预算不应扣除它。成本按实际 Provider 的读取/写入/输出计费口径计算；不能用平均每请求百分比或为了凑缓存阈值增加无关文本来证明改善。

本地前缀对比证明的是请求稳定性。真实命中还依赖服务端落盘、路由、保留时间与模型，不能预先承诺某个百分比。Feature 005 的历史 Report 也明确其有限冒烟没有建立命中率统计结论。

- **目录落点。** 开发者明确指定“项目根目录的 `memory` 目录”。结合当前 Anthias 应用数据与任务 Workspace 分离的方式，本轮按 Anthias 项目根的 `memory/` 理解；当前本地路径对应 `C:\projects\anthias\memory`。这是目录含义的当前解释，具体文件结构尚未确定，也未创建运行时记忆目录。
- **分层含义。** 开发者明确要求包含“用户的 memory”以及“Agent 会自己记一些东西”的另一类。讨论中暂称为“用户记忆”和“经验记忆”：前者围绕用户偏好、习惯与长期要求，后者围绕任务中得到的可复用经验、验证结论和适用条件。分类依据是记忆内容；用户记忆也可以由 Agent 从用户表达与纠正中提取，不能把两类简单等同于人工写入和自动写入。

- **范围与时效。** 存放在同一根目录不代表所有项目都采用全部记忆；用户偏好与项目经验仍需要适用范围。分层与有效性分别表达，具体期限、复核和候选处理尚未定稿。
- **更新方式。** 延续前述稳定前缀原则：有效记忆可以更新，当前会话通过有来源的追加内容表达变化；新会话或压缩重建采用最新有效状态。用户要求某项内容不再发送时，后续模型上下文需要移除该内容。

### 2026-09-07：项目规则自动加载与优先级

开发者明确将 `AGENTS.md` 自动加载纳入 Feature 008，并给出以下三层优先级：

> 项目规则（AGENTS.md） > 有效经验记忆 > 用户记忆。

项目规则继续以任务项目中的文件为来源，两类记忆由 `memory/` 保存。这里的“用户”按长期用户记忆理解；当前真实用户的明确要求仍优先于上述三层，现有权限和硬禁止边界继续由 Agent 执行。先过滤不适用、过期或待核验的内容，再处理同一事项的冲突；层级不能把旧记忆变成已核实的当前事实。

本轮建议首版自动加载当前任务项目根目录的 `AGENTS.md`，不把 Anthias 自身仓库的规则套到所有任务项目。会话建立和压缩重建时读取有效版本；只查看历史时呈现已保存内容，继续运行前核对当前文件并追加差异；活动会话在下一轮请求准备时检查该文件是否变化，仅对真实变化追加带来源、版本和替代关系的说明。文件不存在时正常继续，读取失败时明确诊断。项目根定位及嵌套目录规则的范围由 Spec 明确，本轮未默认扩展多级继承。

### 2026-09-07：明确的提示词编排建议，待 Spec 确认

内容优先级与排列顺序分别表达：基础规则声明上述冲突规则，每段上下文保留来源和有效版本；文本按复用范围及变化频率组织。初始上下文建议采用以下固定顺序：

| 顺序 | 内容 | 保持稳定的方式 |
| --- | --- | --- |
| 1 | Anthias 通用基础规则，包括行为边界、来源优先级和记忆使用规则 | 放在固定 system 部分，不混入路径、每轮时间或实时状态 |
| 2 | 少量稳定的用户记忆摘要 | 只选跨任务适用的明确偏好；会话开始选定，后续变化追加 |
| 3 | 工作区、平台、Shell 与初始权限模式 | 保存该会话的环境视图；实际执行继续核对当前权限 |
| 4 | 当前任务项目的 AGENTS.md | 初始版本固定，普通文件变化追加新版本与替代说明 |
| 5 | 当前工作区可用 Skill 等能力的紧凑目录 | 只放发现所需元数据，无语义顺序的条目确定性排序；正文按需加载 |
| 6 | 经验记忆的紧凑索引与少量已选有效条目 | 限定项目、条件和预算；后续检索结果及更新追加 |
| 7 | 对话、Tool 结果、成员输入及动态来源 | 按真实发生顺序追加；Skill / MCP 正文、记忆读取、规则更新保留各自来源 |

用户记忆排在项目内容之前，是为了让跨项目共用的稳定偏好形成更长的公共前缀；它在规则冲突时仍低于项目规则和有效经验。第 2 至 6 项是会话初始视图，不能随每轮检索、最后访问时间或目录刷新重新拼写。若一项内容必须从后续请求中移除，则重建相关上下文；追加“已忘记”本身不能完成移除。

`tools` 在当前 Adapter 中是独立请求字段，不复制成一份完整文本塞入上述顺序。对相同可用工具集合，稳定名称、描述、schema 和排列；工具增删及权限变化仍如实更新。Provider 决定最终的工具与消息渲染方式，调换 JavaScript 对象属性不能控制服务端前缀。上述表格规定 Anthias 的内容装配顺序，具体消息 role、Schema、来源持久化及投影接口仍由 Spec / Plan 落实。

验收需覆盖项目规则自动加载和刷新、三层冲突处理、普通增量保持既有前缀、动态正文追加、恢复或遗忘后的有效版本，以及工具集合实际变化的可解释性。

结论：当前范围足以形成 Feature 008 首版，可以进入 Spec 收敛。项目规则自动加载、两类记忆、主动维护、范围与时效、双入口以及提示词顺序已覆盖用户主线；直接实施前还需明确以下行为。开发者随后认可了下表的行为边界；尚未提出或选定的默认值仍由 Spec 明确。

## 对话历史与上下文映射方案（2026-09-07）

开发者认可上一节充分性检查的行为边界，并要求先明确历史与上下文的映射。方案保留三个不同对象：Session 记录该会话实际发生过什么，memory/ 保存跨会话当前有效的记忆，Context 为下一次模型请求选择并编排工作视图。TUI 和模型分别从有来源的会话记录取用内容，压缩不覆盖原始聊天记录。

### 当前已有基础与需要改变的关联方式

当前 Session.messageHistory 由 message 记录构成；Skill / MCP 另存 context_source。Context 的 projectContextHistory 读取压缩检查点，把模型历史变成摘要和保留原文；活动来源当前由 external.project 整体拼入 system。普通 Message 不携带 Session entryId，selection.ts 的 associateRawMessages 还会按顺序和内容匹配寻找持久记录。

新增项目规则、记忆快照和来源更新后，建议在 Agent 内部直接携带对应的 entryId / seq，并让来源条目携带 sourceId 与版本指纹。正文相同的两条用户消息仍是两条不同历史；规则文本与用户文本相同也不构成同一种身份。Loop 的本轮执行视图、Context 投影和 Session 持久记录用这些身份关联，TUI 不承担匹配和重建。

### 来源记录与模型视图

| 内容 | Session 中保存什么 | 普通模型请求中怎样使用 |
| --- | --- | --- |
| 用户、Assistant 与 Tool 消息 | 原消息及 entryId / seq，Tool 保留调用 ID、结果状态、受限预览和原文产物引用 | 未压缩部分对应原消息；旧部分可以由带覆盖范围的摘要替代 |
| AGENTS.md 与选中的用户/经验记忆 | 本会话实际采用的有界来源快照、来源 ID、版本、范围与后续更新 | 初始快照进入固定位置；普通变更以新版本和替代关系追加 |
| 按需读取的 Skill / MCP / 记忆正文 | 已读取内容的来源快照，关联触发的读取行为 | 在对应读取完成后追加一次正文，避免 Tool 结果和额外来源块重复注入全文 |
| 成员任务与消息 | 继续保留独立的 agent_input 来源 | 只投影明确投递到该 Session 的内容，不复制成员的全部历史 |
| 压缩结果 | 摘要、覆盖的历史范围、保留消息身份，以及该检查点采用的来源版本与已折叠更新边界 | 作为标明派生性质的摘要使用；来源快照单独维护，后续增量继续追加 |
| Run 状态、用量、审批等控制记录 | 原样作为控制和审计事实保存 | 按用途选择，不能机械地把整份 JSONL 都转成模型消息 |

每个投影块都要能说明它来自哪条消息、哪个来源版本或哪组被摘要覆盖的记录。固定 system 规则和 tools 由当前受控配置提供，继续与上述来源区分；本轮不要求另存一套完整的请求正文副本。

项目规则和记忆保存为来源记录，不写成真实 user 消息记录。在当前 OpenAI-compatible 协议内，建议复用内部输入的投影方式，将其包装成明确标注来源的 user role 上下文块；协议 role 不等于会话中的发言者或授权身份。真实 Tool 结果继续对应实际 ToolCall，不为上下文注入制造不存在的调用。

来源可能在 Tool 执行期间先落盘、随后才产生 ToolResult，因此模型投影不能机械按 JSONL 行顺序插入正文。由工具读取引出的来源块应放在完整 ToolCall / ToolResult 组之后；更新保留自身事件顺序和所属组关联。任何压缩和来源刷新都不能拆开未闭合工具组。

### 普通更新、压缩和恢复

普通对话中，初始来源视图保持稳定；新对话、读取结果和来源更新在合法消息边界追加。例如项目规则 P1 与记忆 M1 已进入前缀，后来保存 M2，则当前请求采用“原前缀 + 已有完整对话 + M2 替代 M1 的来源更新 + 后续消息”。磁盘当前值成为 M2，原会话记录仍能解释何时使用过 M1。

压缩完成后，请求可以变为“固定基础规则 + 已核对有效的初始来源视图 + 历史摘要 + 明确保留的原消息/完整工具组 + 检查点之后的新消息和来源更新”。压缩检查点除对话覆盖范围外，还需记录来源快照及已折叠的来源更新边界，避免重放旧更新或重复插入最新正文。摘要记录任务经过和未完成事项；当前项目规则与记忆以独立有效来源为准。

原始记录保持原样；只有候选摘要、来源视图和映射边界全部校验并成功保存后，才切换模型投影。失败或取消时继续保留已提交视图，不能留下只在内存中生效的半次压缩；取消后不再发起模型请求。原始 Reasoning 仍只用于当前 Run 的临时续传，不因缓存目标而新增持久化。

恢复分两步：只查看历史时展示已保存事实，不读取当前 memory/ 来改写过去，也不重新执行 Tool；明确继续任务时，先按已保存检查点和来源事件恢复投影，再核对当前规则和有效记忆，把差异作为新的来源更新保存。遗忘、必须停止发送的内容或不再可用的摘要需要过滤或重建相关模型视图，不以保持旧前缀为由继续发送。停止采用记忆与彻底擦除原始会话记录仍是两个操作。

普通回答、摘要和 AutoAllow 继续使用各自的输入边界。来源投影由 Agent 的 Context 统一负责；AutoAllow 仍从真实用户消息和动作相关的人工批准取证，不从模型 role、记忆、摘要或成员转述推导授权。

### 映射验收
