# Anthias 开发流程

## 目的

Anthias 由开发者长期主导，Agent 辅助讨论、研究、实现和审查。本流程让每个增量范围清楚、能够运行、可以验证，并确保产品决定和代码实施不会被混在一起。

开发者负责产品方向、关键取舍、实施授权、Git 动作和最终验收。Agent 负责核对现状、澄清问题、形成可检查的方案、完成被授权的修改并报告证据。

当前对话、仓库状态和实际运行结果是工作的直接输入。历史报告和研究材料只提供线索，不能覆盖当前事实或开发者的新决定。

## 选择工作路径

先根据问题本身选择最短但完整的路径：

| 类型 | 适用情况 | 默认路径 |
| --- | --- | --- |
| 讨论 | 产品方向、术语或取舍尚未确认 | 核对现状 → 讨论 → 记录已确认决定 |
| Research | 关键事实需要外部证据，或方案存在明显未知 | 定义问题 → 限定来源与时效 → 调查 → 记录证据边界 |
| 小型修改 | 文案、局部缺陷或低风险内部调整 | 明确结果 → 允许实施 → 聚焦验证 → 汇报 |
| 中型 Feature | 一个完整用户行为或重要内部合同 | Spec → Plan → 允许实施 → 验证 → 验收 |
| 大型 Feature | 多个可独立验收的能力或跨边界改造 | Spec → 分 Stage Plan → 逐 Stage 实施和验收 |
| 项目基线 | 产品定义、技术基线或协作规则变化 | 只读核查 → 文档草案 → 开发者确认 → 更新文档 |

代码行数不决定工作类型。公开行为、执行与取消语义、副作用、数据格式、模块职责或迁移方式发生变化时，应提高审查和验证强度。

## 状态与授权

中大型 Feature 使用以下状态：

```text
Draft → Specified → Planned → Implementing → Implemented → Accepted
```

- `Draft`：问题或方案仍可调整。
- `Specified`：产品行为、范围、失败表现和验收标准已确认。
- `Planned`：实施顺序、验证方式和停止条件已确认。
- `Implementing`：开发者已经明确允许修改代码。
- `Implemented`：实现和约定验证完成，等待验收。
- `Accepted`：开发者确认产品表现和证据边界。

讨论确认、`Specified` 和 `Planned` 都不授权修改代码。实施、Git 初始化、提交、推送和创建 PR 是独立动作，不能相互推断授权。

## 标准流程

### 1. 核对问题与基线

开始前进行只读核查：

1. 确认当前目录、分支、工作区和已有修改。
2. 阅读与请求直接相关的产品文档、代码入口、测试和运行配置。
3. 找到真实调用链或需要建立的用户闭环。
4. 明确目标、非目标、失败表现、验收结果和需要开发者决定的事项。

完成标准：能够用当前证据说明为什么要做、做到哪里，以及哪些内容不在本次范围内。用户只要求讨论、诊断或审查时，到对应结论后停止。

### 2. 必要时 Research

只有关键决定确实依赖外部事实时才进入 Research。开始前说明研究问题、来源优先级、截止时间和输出用途；优先使用官方文档、规范、源码和论文原文。

研究结论要区分来源事实、项目推断和建议，写明无法证明的部分。完成的调查移入 `research/archive/`；归档材料不自动改变产品定义或 Feature。

完成标准：关键主张可以追溯，时效和证据边界清楚，并且结论已经回到 Anthias 的实际问题，而不是停留在外部项目介绍。

### 3. 确认 Spec

中大型 Feature 在 `specs/features/NNN-feature-name/spec.md` 保存产品合同。Spec 聚焦问题、用户流程、行为与失败、关键决定、非目标和验收标准；只在确有需要时增加术语、状态或生命周期说明。

Spec 不记录实施流水账，也不用文件清单代替用户行为。开发者确认后才能标记为 `Specified`。

完成标准：执行者不需要自行补作关键产品决定，就能判断 Feature 做成和没做成的区别。

### 4. 确认 Plan

Plan 与 Spec 放在同一 Feature 目录，说明当前基线、范围、实施顺序、验证方式、风险和停止条件。大型 Feature 拆成线性 Stage，每个 Stage 只交付一个可独立检查的增量。

Plan 可以为低风险实现细节留出调整空间，但不能把产品语义、公开合同、模块职责或 Feature 范围留给执行 Agent 临场决定。

完成标准：执行者可以在已确认边界内完成当前 Stage，并知道何时必须停止。

### 5. 取得实施授权

只有开发者明确要求开始实现，才修改代码。授权只覆盖当前确认的 Feature 或 Stage，不自动覆盖后续 Stage、真实外部调用和 Git 动作。

### 6. 实施与验证

执行 Agent 必须：

1. 再次检查工作区，保护已有和无关修改。
2. 只修改当前 Feature 或 Stage 所需文件。
3. 优先完成简单、完整的调用链，不预建空模块、假接口或未来框架。
4. 运行与当前风险相称的验证。
5. 发现范围、语义、公开合同或模块职责变化时停止并回到讨论。

验证优先覆盖公开行为、取消、失败传播、资源释放和实际交互状态恢复。真实模型、外部网络、付费 API、敏感凭据或外部状态变更的验证必须单独授权。

完成标准：当前 Stage 可以独立运行或检查，没有暗中带入后续范围，也没有未说明的工作区影响。

### 7. 汇报与验收

实施报告至少说明：

1. 已完成的用户行为和明确未完成的范围。
2. 入口、主要调用链和关键职责。
3. 取消、并发、失败和资源释放中的重要边界。
4. 实际运行的验证命令、结果和环境。
5. 外部服务、真实模型和人工体验中尚未验证的部分。
6. 当前 Git 状态和提交前需要检查的变更范围。

一个 Stage 汇报后停止。只有开发者可以把 Feature 标记为 `Accepted`。验收后，再把已经成立的能力同步到 `README.md`、稳定 `docs/` 和 Feature `report.md`。

## Agent 交接与验证复用

交给执行 Agent 的任务必须包含：

- 当前代码和文档检查点；
- 当前 Stage 的目标、允许修改区域和禁止范围；
- 必须运行的验证命令和外部权限限制；
- 报告需要包含的完成内容、验证结果、风险与 Git 状态；
- 语义变化、重叠修改、迁移风险或凭据风险等停止条件。

执行 Agent 自己运行约定验证并汇报。相同代码版本、环境和命令已经有可信结果时，接手 Agent 不重复运行，只在代码变化、证据缺失或验收目标不同的情况下补足缺口。

普通实现错误优先由原执行 Agent 在同一范围内修复。测试失败先诊断原因，不靠反复重跑碰运气。

## 代码约定

当前没有已确认的编程语言或工具链，因此不保留 Java 专属的包名、格式化、类型、异常、注释和测试约定。新技术基线确认后，只加入该语言真实需要且能改变执行质量的规则；可直接从构建配置和目录结构读取的事实不在本文重复缓存。

## Git、配置与文档

- 工作区已有修改属于开发者；不重置、不清理、不覆盖无关内容。
- 中小更新避免拆成大量提交；大型更新只在存在独立验收价值时使用阶段提交。
- 提交前先让开发者检查变更范围；提交、推送和 PR 分别取得授权。
- API Key、Endpoint 和账号信息只通过被忽略的本地文件或环境变量提供。
- `README.md` 和稳定 `docs/` 要区分已确认决定与已实现能力；尚未实现的 Feature 行为保存在带状态的 Spec / Plan 中。
- 临时提示词、Agent 草稿、工作日志和测试输出不进入长期文档。
