## 结论

界面成员的浏览器命令超时，运行时无法确认进程清理完成，于是保留工作区独占锁。保留写入保护有必要，但这条锁没有可用的回收入口：已排队的文件写入、后续命令和根的列目录请求持续等待；停止后再次开始也没有恢复工作区。

运行时只呈现了成员阶段，未把清理不明升级为根可处理的阻塞事实。根随后声称“没卡住”，并重复提交同类命令，进一步延长了等待。低输出预算和冗长协作反馈同时增加了失败与上下文开销。

调查基线确认了“清理不明 → 保留独占锁 → 后续受管写入阻塞”的链条。[Feature 015](../../specs/feature015-execution-recovery/report.md) 已将残留租约改为可查询、可恢复的显式阻塞，并结束受影响的排队。浏览器命令最初为什么没有正常结束仍待查证，不能把成员关于 daemon 生命周期的解释当作根因。

## 原因分析

### 1. 写入保护缺少异常后的恢复路径

工作区锁用于协调本进程管理的副作用：

- 内建文件编辑按真实文件身份串行；取得写入权后重新检查内容版本，再原子替换。不同文件可以并行修改。
- 通用命令可能修改任意文件，不能仅凭“列目录”的正文认定为只读，因此 `execute_command` 对相关工作区取得独占写入权；Git 操作也使用协调器。
- 模型思考、批准等待和组内通信不应持有工作区写锁。这不是 OS 沙箱，外部编辑器或其他进程不受它完整约束。

正常顺序是：

~~~text
完成批准 → 等待写入权 → 再核对执行前提 → 执行
→ 确认执行与资源清理结果 → 释放写入权 → 后续操作继续
~~~

本次异常顺序是：

~~~text
界面成员取得工作区独占锁 → 启动浏览器命令
→ 命令超时 → 清理无法确认 → 返回 cleanupUncertain
→ 跳过释放锁，且没有可用的回收入口
→ 文件写入、成员命令和根命令持续排队
~~~

调查基线的 `executePreparedCommand` 根据 `cleanupUncertain` 设置 `retainWriteLease`，在 `finally` 中跳过释放。`workspace-access.ts` 只有租约的释放回调会移除活动写入；已经取得租约后，取消信号不再负责撤销它。命令收口还会移除子进程监听器，当前路径没有迟到清理结果解除这条保留锁的机制。

因此，停止当前 Run 能取消排队，却不能回收此前因清理不明而保留的锁。这是缺少回收入口的独占锁保留，现有证据没有显示循环等待型死锁。Run 总截止时间仍能取消等待，但不会凭空证明旧资源已经安全退出。

直接无条件释放也不成立：清理不明时，旧进程可能仍在写工作区。修复应保留写入保护，并补足阻塞事实、通知与恢复流程。

### 2. 工具等待和异常反馈没有给根足够依据

命令的计时与超时预算从取得锁、启动子进程后开始，不覆盖取锁等待。`tool_execution_started` 又早于实际取得工作区锁，因此界面显示“工具已开始”不代表进程已启动。本次 `durationMs: 0` 与取锁时取消一致，不能解释为列目录执行了数分钟。

成员状态能反映 `awaiting_workspace`，但不能告诉根谁持有锁、为什么未释放、能否恢复。`agent_wait` 主要在选中成员不再忙碌时提前返回，模型重试、清理不明等事件虽然可转发到界面，却没有形成根可处理的故障摘要或通知。

另外，根把 `execute_command` 与 `agent_list` 放在同一批次时，前面的串行命令阻挡了后面的状态查询。根应依据事实承认执行受阻；运行时也必须让诊断和停止入口在工作区阻塞时仍可用，不能只靠提示词纠正“没卡住”的说法。

### 3. 输出预算不足，且实际生效配置难以核对

粒子成员两次输出达到 16,000 Token，第二次工具参数不完整而未执行。这一事实来自当次日志。调查时安全读取的本地配置为：模型调用名 `deepseek-flash`，上下文窗口 128,000，模型最大输出与普通回复预算均为 16,000，压缩预算 8,000。该读取只包含允许列出的非敏感字段，不是事发进程的完整配置快照。

调查基线代码与模板已有普通输出默认 64,000 的策略，但显式配置的 16,000 会覆盖默认值；只改模板无法修复已有本地配置。能力表仍登记 `deepseek-v4-flash`，没有匹配实际调用名，说明配置与能力信息也需要同步核对。

用户使用 `deepseek-flash` 并非命名错误。[DeepSeek 2026-09-10 的官方公告](https://deepseek.com/news/deepseek-v4-1-flash/) 已说明 V4.1 Flash 使用这个调用名。模型实际容量应以实施时核验的官方能力为准，不从旧能力表推断，也不为此引入模型专用执行分支。

预算不足解释了粒子成员的输出失败，不解释浏览器超时或锁未释放；提高预算不能代替运行时修复。

### 4. 协作输出与文件编辑反馈增加了重复工作

根的三次正常等待结果每次约 7.5 KB，重复包含三个成员的完整任务；成员最初查询群组的结果约 14.7 KB，部分还需通过产物回读。关键信息“谁阻塞了工作区、是否需要处理”反而不突出。

成功的文件写入与编辑只返回完成提示，没有返回新内容版本。音频成员两次因过期版本被拒绝。版本拒绝本身是正确保护，缺口是成功后没有提供下一次编辑可用的版本。

## 解决方案与实施边界

以下行为已按 [Feature 015 Spec](../../specs/feature015-execution-recovery/spec.md) 实现。先保存 Spec 与单一 Plan，再实施；没有增加通用后台服务管理、跨进程接管或完整命令日志。

| 修复方向 | 当前行为 |
| --- | --- |
| 显式工作区阻塞 | 清理不明时保存 `blockId`、工作区、所属 Session、ToolCall、原因与清理事实。由明确的阻塞记录持有写入保护，避免遗留无来源、不可回收的租约。 |
| 结束无效排队 | 进入阻塞后，已排队和后续受影响写入立即返回 `workspace_blocked` 与同一来源标识；不再无声等待，也不启动命令或写文件。 |
| 有界清理与恢复 | 有界检查原操作保留的资源关闭事实；确认完成后解除对应阻塞，失败则保留原因与下一步处理方式。恢复绑定阻塞标识，迟到结果不得解除新的封锁；不能凭可能复用的裸 PID 杀进程。 |
| 根及时获知异常 | 清理不明、工作区阻塞和反复输出超限形成简短通知；`agent_wait` 能因需要根处理而提前返回。普通重试不反复打扰，状态查询保留故障来源和执行事实。 |
| 控制入口可用 | 少量只读状态查询、停止和恢复行为不被等待工作区的命令挡住；普通文件与命令继续遵守现有顺序。 |
| 等待有预算且可解释 | 保留 timeoutMs 的执行时间含义，取锁另使用同一数值作为等待上限。分别报告 waitDurationMs、executionDurationMs 和 processStarted，审批等待不计入。 |
| 明确命令资源生命周期 | 保留原命令的进程与管道关闭证据供恢复检查。清理不能确认时保持阻塞；用户在外部清理后可直接确认，记录确认来源。没有新增浏览器或常驻资源平台。 |
| 校正模型预算 | 核对能力表、调用名与已有配置；普通 Coding 默认输出采用 64,000 并受已核验模型能力约束，摘要和审核保持独立预算。展示脱敏后的配置来源、最终值，并记录实际请求采用的预算。 |
| 减少协作反馈负担 | 列表与等待默认返回简短状态、变化和故障，完整任务与历史按需读取；成功写入、编辑返回实际提交后的 `newVersion`，继续拒绝过期版本覆盖。 |

恢复不等于重试原操作。解除阻塞后，新的副作用仍需按当前权限、文件版本与取消状态重新校验，不能自动重放已完成工具。停止成员、关闭成员、发送新消息或重启 Anthias 都不构成资源已清理的证明。

遇到同类现象，使用 `/agents` 查看 blockId、所有者和原因，`/agent recover <blockId>` 检查原资源。若仍无法确认，由用户外部清理后输入 `/agent recover <blockId> confirm-cleanup`。模型不能伪造该确认。已发生的阻塞保存在 Session 数据目录的 `workspace-blocks/`，重启会重新加载；保存失败保留内存保护并明确提示跨重启边界。重启和关闭成员都不构成清理证明。

## 调查后确认的输入交互要求

用户补充了“运行中消息卡在界面”的交互问题，并确认下列目标。这是调查后确认的修复需求，当前日志不足以独立复现消息气泡滞留的具体原因。

- 空闲时 Enter 直接开始；运行时 Enter 默认进入 `followUp`，输入被接受后清空编辑区，并明确显示排队状态。
- 运行中有待处理用户消息时，一次 Esc 立即请求打断当前回答，提升最早一条消息；沿用原 `inputId`，保留其余消息顺序，连续 Esc 不重复投递。未提交草稿不自动发送。
- Esc 对应根当前输入的中断，不直接调用整组停止。其他成员不因这次输入中断自动暂停；共享工作区若进入阻塞，它们的受影响操作仍受同一保护约束。Ctrl+C 保持明确停止群组的含义。
- 没有待处理消息时，Esc 保留关闭详情、补全等界面行为。输入提升应优先于这些普通界面操作。
- 插入消息不得重置群组原有共享时限；用户明确停止后，待处理输入保持暂停。

**必须遵守的取消与清理顺序：**

~~~text
Esc 请求提升同一条输入
→ 立即请求取消当前模型流、所属工具、批准与资源等待
→ 保留已成功工具的结果，给未完成或未执行调用补齐准确终态
→ 等待必要资源清理，正确结束旧 Run
→ 确认清理完成后，再启动处理该输入的新 Run
~~~

“立即”指立即发出取消请求，不表示立即宣称资源已释放。工具已经成功产生的副作用不回滚、不重放；未启动的工具不能被记成已执行。

清理无法确认时，必须明确报告阻塞来源，保留输入身份与待处理状态，允许通过控制入口诊断和恢复；不能把消息标成已消费后丢失，也不能以开始新 Run 为由跳过清理。界面应区分“正在打断并清理”“清理受阻”和“正在处理你的消息”。

## 修复验证与剩余问题

必要的定向回归已经通过：

- 输出管道或进程清理不明后建立阻塞，已排队和新写入明确失败；命令破坏 cwd 时仍以原租约资源键保持保护。
- 检查未通过、阻塞保存或恢复写盘失败时保持保护；通过原句柄证据或用户直接确认后只解除对应阻塞；旧标识不能解除新阻塞。
- 命令等待超时不启动进程；成功编辑返回可继续使用的新版本，旧版本保护仍通过原有并发用例。
