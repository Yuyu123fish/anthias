# Anthias 产品定义

## 当前状态

状态：截至 2026-09-12，当前实现包含 Coding Agent、全屏 TUI、上下文与记忆、多 Agent 协作和执行恢复；工程验证方向已确认，专用能力留待后续 Feature。

Feature 003、005 已验收。当前协作以 Feature 014、执行恢复以 Feature 015 为准；其他功能的完成情况和验收边界见 [Feature 索引](../specs/README.md)及各自 Report。发布仓库不改变这些验收状态。

## 产品定位

Anthias 是一个本地优先、交互形态无关的 Coding Agent。当前先完善日常编码能力，后续围绕工程问题组织验证，帮助开发者判断系统行为和编码结果。

首先服务个人开发者：他们能够提出需求、查看代码或操作应用，但未必熟悉如何准备数据、设计验证、解释测量结果。Anthias 希望帮助他们获得足以支持接受修改、要求修复或暂缓判断的事实依据。

已确认的后续产品目标是：

> 把开发者对系统的疑问，转化为可执行、可复现的验证，并根据实际证据解释结果。

验证可以面向 Anthias 或其他 Coding Agent 完成的代码，也可以用于已有系统。对象不限于页面或全栈项目，还包括接口、命令行程序、并发逻辑、性能、数据一致性和故障恢复。缺少现成手段时，Agent 可以利用 Coding 能力编写数据准备脚本、请求驱动、检查程序或观测辅助代码。

执行分叉不再承担产品定位，也不再是必须实现的后续目标。

## 产品形态

Anthias 是本地优先、交互形态无关的 Coding Agent。

    Anthias Agent（运行核心）
      ├─ TUI 适配器
      └─ Desktop 适配器

- Agent 持有消息、模型运行、运行状态以及后续 Tool 和工作区副作用，是行为权威。
- TUI 是首个交互入口，直接调用 Agent，并根据 AgentEvent 呈现运行过程。
- Desktop 是未来可加入的交互适配器。它可以转发同一组 Agent 命令和事件，但不产生另一套 Agent 状态。
- Agent 的公开接口不依赖终端库、Electron、React、MessagePort 或传输协议。
- 当前不建设云端后端或公共网络服务；是否需要独立本地进程，由具体交互 Feature 决定。

## 近期重点：补齐 Coding Agent 基本功能

当前优先完成一个可复用的 Coding Harness，使实际编码工作所需的基础行为足够可靠：

- 模型消息与多轮上下文；
- 流式 Assistant 输出；
- Agent 生命周期、取消和失败恢复；
- Tool 定义、调用和结果回传；
- 文件、编辑和命令等本地能力；
- 权限、资源释放和可观察事件；
- Session 与上下文管理。

上述能力已有不同程度的实现，不代表每项都需要重新建设。剩余缺口以当前代码、运行结果和实际使用为依据，逐项讨论并确定对应 Feature。

推进顺序已经确认：先补齐 Coding Agent 剩余基本功能，再开展工程验证能力的 Spec、Plan 与实现。本次只确认产品方向，不提前建立验证框架、数据平台、证据存储模型或新的公开接口。

## 后续工程验证方向（尚未实现）

一次验证任务应从开发者想回答的问题出发，形成以下工作过程：

1. 明确判断依据。结合需求、业务规则和代码确定要检查的行为、适用条件与成功标准；无法确认的规则显式列出。当前实现是调查对象，不能单独作为正确性的依据。
2. 准备环境与数据。记录目标版本和运行条件，准备有明确关联与状态的数据。体验数据便于浏览和演示；验收数据保持受控、可重复初始化，并能清理本次准备的内容。
3. 构造验证手段。选择已有工具，必要时编写脚本、并发驱动、检查程序或观测辅助代码。生成的程序也需要检查其行为，确认它确实触发目标场景并能识别异常。
4. 执行与核对。结合操作结果、接口响应、日志和必要的数据状态检查回答问题。异步受理与最终完成分别核对；业务拒绝与技术错误分别记录。无法获得足够证据时保留未验证结论。
5. 交付证据与结论。保留判断依据、环境与数据说明、可执行的验证程序和实际结果，使开发者能够检查依据并重复执行。结论区分通过、失败和尚不能确定，并说明适用范围。

例如，验证秒杀接口是否超卖，可以准备已知库存和多个用户，构造集中请求与重复提交，再核对最终有效订单、库存变化和异步处理结果。验证性能时需要记录实际达到的负载、响应时间分布与错误分类；未确定性能目标时先提供测量依据，不自行宣称达标。具体规则、负载与观测时限由任务确定，这个例子不构成已经实现的秒杀验证能力。

利用 Coding 能力补齐验证手段，服务于当前验证问题。若需要修改被测代码，应记录改动与实际受测版本；业务修复和修改验收标准不能被隐含在数据准备或观测代码中。生成脚本仍经过既有工具权限与资源管理，不自动获得新的执行权限，也不意味着 Agent 可以自行改造自身运行核心。

一次验证首先回答特定版本在特定条件下的行为。比较不同 Coding Agent 的质量，还需要可比较的任务、环境、数据与多次执行证据；单次演示或一个总分不能代替这些依据。

## 当前实现状态

- 仓库已有可构建、可启动的 Agent 与对话式 TUI；生产 OpenAI-compatible Model Adapter、线性 Session、Tool 和运行生命周期位于 Agent Module 内部，TUI 不持有这些行为权威。
- 旧的 Electron Desktop、Utility Process Host、JSON-RPC、Protocol DTO 和 Renderer 状态投影已经撤销。
- Feature 001–003 已累计实现多轮模型与 Tool 循环、六个固定 Tool、线性 JSONL Session、工作区文件和命令能力、逐次副作用确认、权限模式（当前为请求批准、AutoAllow 和 Full Access）、`allow | ask | deny` 安全决策与只读 Tool 四并发；Feature 003 已由开发者验收。
- 当前命令仍以 Anthias 所在用户权限运行，没有 OS 沙箱；真实 Provider 只有 Feature 005 报告所列的有限冒烟，长期人工终端体验仍待验收。
- [Feature 006](../specs/feature006-command-skill-mcp-tui/spec.md) 已实现全屏 TUI、常用命令、外部 Skill 按需加载与 MCP 接入。正文支持可见滑块和鼠标滚动，任务结束后折叠执行过程，并可点击逐级展开；最终回答保持在主体中。会话和能力仍由 Agent 管理，外部内容不增加用户授权；当前交互替代了下面 Feature 004 的历史布局，主观体验待验收。
- [Feature 004](../specs/feature004-tui-workspace-experience/spec.md) 已在本地实现现代对话层级：稳定 scrollback 与底部动态区域并存，完整 Workspace、模式、Session 和 Run 状态持续可见；Visible Reasoning 自动折叠并可用 `/details` 回看，超出终端高度时通过 `/details prev|next` 分页；Tool 按 `toolCallId` 呈现摘要与详情，Assistant 文件引用经 Workspace 校验，已标记代码块由 Shiki 按需着色。运行中窗口小到无法安全保留上下文时会暂停提交和确认，放大后恢复；非 TTY、无颜色和无 Unicode 均有等价降级。
- Feature 004 的自动门禁和 Windows ConPTY loopback 已通过；真实 DeepSeek V4 Flash 冒烟与 Windows Terminal 主观视觉检查尚未完成，因此尚未进入“已实现”状态。
- Feature 005 已于 2026-09-05 由开发者验收，形成上下文压缩和自动继续、完整历史与模型投影分离、工具原文访问、两周未使用会话的启动清理，以及 AutoAllow 模式。自动审核只能依据真实用户授权，不能覆盖硬禁止策略。
- Feature 007 建立本地 Git 成果交付与协作历史；其 SubAgent/Team 和自动工作树规则由 [Feature 014](../specs/feature014-unified-multi-agent/spec.md) 的统一持续成员替代。根统筹成员、邮箱和唯一共享笔记，默认共享工作区，按任务需要显式隔离；用户高于根，根高于成员，组内内容不构成用户授权。实现与验收状态见 [Report](../specs/feature014-unified-multi-agent/report.md)。
- 工程验证方向尚未进入对应 Feature；数据准备、验证程序构造与证据交付尚未形成专门的产品闭环。Desktop 尚未实现。

## 核心产品术语

### 编码任务

用户希望 Anthias 在一个代码库中完成或推进的一项目标，包含理解代码、修改、运行与检查相关行为。

### 验证任务

围绕一个明确工程问题，在约定的目标版本、环境和数据条件下收集证据并作出判断的工作。它可以独立于编码任务，也可以用于验收一次编码结果。

### 验证手段

为回答问题而选择的工具、准备的数据、编写的程序和执行方法。其作用是触发所需场景并获得证据，不能以程序成功退出代替对目标行为的检查。

### 验证结论

依据实际证据，对目标行为给出的通过、失败或尚不能确定的判断。结论需要关联判断条件与证据，并保留未覆盖的边界。

## 已确认的产品边界

- 当前优先补齐 Coding Agent 基本功能，后续再实现工程验证能力。
- 工程验证覆盖不同工程对象，允许使用工具和 Coding 能力构造验证手段；具体测试框架和工具清单尚未确认。
- TUI 是首个交互入口，Desktop 是未来可选的适配器，不是产品前提。
- Agent 通过小而稳定的命令与事件接口被不同交互形态使用。
- 一个交互适配器只负责输入和呈现，不复制 Agent 的消息、生命周期或副作用权威。
- Git worktree 等隔离机制按具体任务需要选择；执行分叉、多 Agent 编排与 Agent 自我进化都不是当前产品前提。
- 模型可以使用远程服务，Agent 执行和本地副作用默认发生在用户机器上；实际操作继续遵循权限、取消与资源释放合同。
- 生成验证程序和完成一次验证，不自动授权修改业务实现、改变验收标准或扩大外部执行范围。
