# Anthias 产品定义

## 当前状态

状态：产品路线已确认，首个产品闭环待收束

2026-08-30，开发者撤销了此前围绕 Java/JVM、本地全屏 TUI、`Model + Agent Loop + Tool` 固定概念和 Feature 001/002 形成的产品决定。旧文档和实现只保留在 Git 历史中，不再构成 Anthias 的当前产品合同。

同日，开发者确认 Anthias 的新产品路线：做一个**可分叉的 Coding Agent**。这一决定确认产品的核心差异，但不自动确认技术基线、交互入口、首个 Feature 或实现方式。

## 产品定位

Anthias 把一次编码任务表示为一棵可以产生不同候选方向的执行树，而不只是一段只能沿单一路径继续的对话。

当任务出现多个值得保留的解决方向时，用户可以从共同的检查点创建互不覆盖的执行分支，让它们分别继续，并根据各自结果选择后续采用的方向。

Anthias 的核心价值是：

> 不要求 Agent 在岔路口只做一次不可逆的选择；保留岔路，分别推进，再由用户比较和选择。

## 核心产品术语

### 编码任务

用户希望 Anthias 在一个代码库中完成或推进的一项目标。一次编码任务可以只有一条执行路径，也可以包含多个执行分支。

### 检查点

编码任务中可作为后续共同起点的已知状态。检查点让不同执行分支从同一任务位置出发；它在存储和运行时中的具体表示尚未决定。

### 执行分支

从一个检查点开始、可以独立继续的候选解决方向。不同执行分支后续产生的上下文、代码候选变化和执行结果不能彼此静默覆盖。

“执行分支”是 Anthias 的产品概念，不等同于 Git 分支。Git branch、worktree、补丁、文件覆盖层或其他机制是否参与实现，由后续技术基线决定。

### 候选结果

一个执行分支在当前阶段形成、可供用户理解和比较的结果。它具体应包含哪些代码变化、验证证据、成本、风险或未决项，仍需在首个产品闭环中确认。

## 已确认的产品边界

- Anthias 是可分叉的 Coding Agent，分叉是用户可感知的核心产品行为，不只是内部调度细节。
- 一个编码任务可以从共同检查点形成两个或更多执行分支。
- 各执行分支能够独立推进，不静默覆盖其他分支的候选状态。
- 用户拥有比较和选择候选方向的最终控制权。
- 分叉不以多 Agent 为前提；同一个 Agent 也可以沿不同执行分支继续。
- 普通代码生成、Tool 调用、隔离修改、Diff 和测试属于支撑产品可信运行的能力，不单独作为 Anthias 的产品差异。

## 明确不等同的方向

- **不是 Git 客户端包装**：执行分支可能借助 Git 实现，但它还包含编码任务的上下文和候选方向。
- **不是对话分叉本身**：只复制聊天记录而不能独立推进代码候选状态，不构成 Anthias 的执行分支。
- **不是多 Agent 编排器**：执行者数量与是否可以分叉是两个独立问题。
- **不是自进化 Agent**：当前路线不包含 Agent 自动修改自身 Prompt、Tool、模型路由、Runtime 或代码的能力。

## 需要重新回答的问题

- Anthias 首先为谁解决什么编码任务；
- 哪个具体场景最能证明分叉比线性执行更有价值；
- 首次分叉由用户主动发起，还是由 Agent 提议后经用户确认；
- 检查点与执行分支需要继承哪些任务状态；
- 用户通过哪些信息比较候选结果，以及选择之后发生什么；
- 交互入口是终端、TUI、CLI、桌面、编辑器集成还是其他形态；
- 分支是否需要跨进程或跨会话持久化与恢复；
- 首个 Feature 应验证哪一项核心价值。

## 确认边界

- 当前已经确认产品路线及“编码任务”“检查点”“执行分支”“候选结果”四个产品术语，但尚未确认完整用户场景、产品形态、模块职责或 Feature。
- 归档 Research 和 Git 历史可以提供反例与证据，但不能自动恢复旧决定。
- TypeScript 当前只是优先候选，不是已经确认的技术基线。
- 新技术基线必须服务于可分叉的产品闭环，不能先选语言再反向塑造产品。
- 当前仓库没有已实现的产品能力；产品路线确认不构成 Spec、Plan 或实施授权。
